## Description
## Description
Accepted OJ-5uq4's project-aware `/api/prepare` still flattens every upload basename into the same per-job upload directory. Distinct uploads with the same basename therefore overwrite one another before preparation, producing a successful but wrong job or an avoidable post-write failure. This predates epic commit `d9ff276`; the connected flow now makes the corruption more visible and blocks the capstone.

## Root Cause
At capstone commit `84d52ce06a3e51f34b8f962462828922f76bf31f`, `app/main.py:203-220`:
- creates `SETTINGS.data_dir/uploads/<job_id>` before examining flattened destination names;
- maps every role to `upload_dir / Path(upload.filename or key).name`;
- opens each destination with `open("wb")`;
- stores the same path under multiple role keys when basenames collide.

A read-only real TestClient probe at the integrated application code used synthetic source bytes plus two reference uploads named `same.png` with distinct synthetic bytes. Result: HTTP 200, one stored `same.png`, `job.json` `reference_1` and `reference_2` paths identical, and stored bytes equaled the second upload, not the first. This is data corruption, not merely a validation inconvenience. Cross-role collisions are also possible because source, references, words, and workflow all flatten into the same namespace.

## USER INTENT
A creator must be able to submit multiple valid files without silent byte loss. If their displayed names cannot safely coexist, the application must reject the request before mutation with a clear rename action; it must never return a prepared job that replaced one input's bytes with another's.

## Required Collision Policy
Implement the fail-closed policy exactly:
- Before creating the upload directory or writing any upload bytes, inspect the flattened basename for every present source/reference/optional auxiliary upload.
- If two present roles resolve to the same basename, return HTTP 422 before any filesystem/job/history mutation. The public error must name the duplicate basename and roles and tell the user to rename one of the uploads before preparing again.
- Do not leak absolute server paths.
- Unique basenames, saved-character preparation, and legacy upload-only preparation remain unchanged.

## Affected Components / DIFF BUDGET
- `app/main.py` — pre-write collision validation for the existing prepare upload flow.
- `tests/test_projects_api.py` — real API collision and compatibility regressions.

Exactly 2 files, under 250 changed LOC. A gross overrun is mandatory PM investigation, not automatic rejection.

## Acceptance Criteria
1. A real API regression submits two distinct synthetic reference bodies both named `same.png`. Preparation returns 422 before writes; the response identifies the shared basename and both reference roles and gives a clear rename action. No job ID is returned.
2. A real API regression covers at least one cross-role basename collision (for example source/reference or reference/auxiliary upload). It is rejected by the same pre-write policy with roles and rename action; no partial upload/job/history state is created.
3. Rejection non-mutation is asserted against a clean temporary data root: no new upload/job directories/files, no SQLite project/history change, no input rewrite, and no server job/status record. Existing pre-request project/character/protected bytes/history remain byte- and record-identical.
4. Unique-basename upload-only prepare still succeeds and stores each original byte stream under its expected basename; saved-character prepare still succeeds without re-uploading references and records isolated project history; existing legacy routes/semantics remain green.
5. The bug's two-reference regression explicitly proves the former 200/overwrite behavior cannot recur: there is no successful manifest with identical `reference_1`/`reference_2` paths and no stored file whose bytes equal only the second upload while the first is lost.
6. Focused API test, full suite, compileall, and touched gates pass using the existing virtualenv, temporary SQLite/workspace, and synthetic fixtures. The known Starlette/httpx warning must be disclosed, not suppressed.
